# 寻鹿 Seekoffer 上线前全站审计报告

审计时间：2026-07-10 至 2026-07-11
审计对象：生产站 `https://www.seekoffer.com.cn` 与当前仓库代码
审计方式：生产环境桌面端/移动端逐页检查、核心交互验证、代码审阅、构建与依赖检查、Supabase 数据与安全顾问检查、GitHub 定时爬虫检查。

> 整改状态（2026-07-11）：本报告保留整改前的现场证据，以下发布阻断项已在本轮完成。当前代码已经通过类型检查、Lint、14 项单元测试、19 项后台安全检查、依赖审计和生产构建。

## 0. 本轮整改结果

- Offer 圈已改为真实数据库内容模型，区分“Offer 动态”和“社区讨论”，支持持久化回复、关注、举报与后台审核；无真实 Offer 时使用诚实空状态，官方讨论明确标识。
- 首页、通知库、Offer 圈、资源库和工作台完成移动端验收，375px 实测无横向溢出；移动端导航改为可展开菜单，并补齐跳转主内容和减少动态效果语义。
- 后台指标恢复为“累计访客”和“注册用户”两种独立口径，不再把匿名设备当作注册用户。
- 通知详情站内链接、canonical 和 sitemap 统一到 `/notices/[id]`；旧工作台入口改为正式重定向并禁止搜索收录。
- Next.js、Supabase SDK、ESLint 和 PostCSS 依赖已更新；`npm audit` 为 0 个漏洞，安全审计恢复并扩充到 19 项。
- 隐私政策、匿名统计同意机制、180 天分析数据清理任务和用户数据权利说明已完成。
- 联系人已纳入云端工作台状态，增加同步状态、冲突时间戳、活动/归档视图和加载骨架。
- 通知公开流新增质量门槛：院校、学院、截止时间或原通知链接不完整的记录不进入主列表；学院可从标题可靠提取，全校通知单独标识。
- 数据库已补齐外键索引、收敛重复 RLS 策略并缓存用户鉴权判断；后台 API 与统计 API 已重新部署。

仍需在 Supabase 控制台手动开启“泄露密码保护”。该开关不阻断当前邮箱验证码登录，但建议在正式开放密码登录前启用。首屏 JavaScript 拆包、自动化读屏检查和完整浏览器 E2E 仍属于后续性能与质量建设项。

## 1. 结论摘要

当前网站已经具备成熟产品的视觉基础，通知发现、通知详情、院校库与申请工作台的主链路基本成立。类型检查、Lint 和生产构建均通过，定时爬虫也在运行。

但当前版本还不适合直接作为“完全可信的商业产品”大规模推广。上线前最需要处理的不是继续堆页面，而是解决以下六个发布阻断项：

1. Offer 圈公开数据与后台数据矛盾，且互动不持久化。
2. 首页和工作台在窄屏手机上存在文字及按钮裁切。
3. “累计用户”实际按浏览器访客标识统计，指标名称和转化率口径不准确。
4. 通知详情存在两套 URL，站内链接与 sitemap/canonical 不一致。
5. 生产依赖仍有高危/严重漏洞，后台安全审计命令本身已失效。
6. 隐私政策没有覆盖网站实际采集的数据类别、用途、保存期限和第三方处理情况。

建议采用“先修可信度和基础设施，再扩内容和增长”的顺序，而不是继续增加新模块。

## 3. 用户视角

### 3.1 第一次访问

健康度：桌面端良好，移动端高风险。

- 桌面端品牌、主功能和核心数据容易理解。
- 窄屏设备出现标题与按钮裁切，顶部导航也没有明显的菜单或横向滚动提示。
- 首页第一屏产品说明充分，但“看通知”与“如何开始管理申请”的关系还不够直接。

建议：移动端改为紧凑品牌栏 + 菜单；首屏只保留一句价值主张、一个主 CTA 和一个次 CTA；在通知卡上直接解释“加入工作台后会发生什么”。

### 3.2 查找通知

健康度：良好。

- 类型、学校层次、报名状态、截止时间等筛选已经能有效缩小范围。
- 985 筛选可正常选中与取消，数据结果会变化。
- 首次载入出现“正在恢复浏览位置”，移动端搜索与结果被大幅推到首屏以下。

建议：移动端将统计摘要压缩为一行，把搜索和当前筛选提前；恢复历史位置时使用不阻断列表的轻量提示。

### 3.3 阅读通知详情

健康度：视觉良好，内容完整性与 SEO 仍需治理。

- 信息字段、截止提醒和加入工作台操作清晰。
- 某些板块在原通知没有结构化内容时，只显示概括性兜底语句，用户仍需要打开原文确认。
- 详情 URL 两套并存，分享和搜索入口不稳定。

建议：对缺失字段明确写“原通知未单独说明”，不要用看似具体但实际无信息的占位文字；保留官方原文作为核验入口，同时页面文案以“寻鹿整理”呈现。

### 3.4 管理申请

健康度：主链路可用，跨设备一致性不足。

- 申请清单、日程和联系人结构已经比传统表格更易用。
- 联系人当前只在本机保存，换设备或清理浏览器后会丢失。
- 远端与本地冲突时缺乏可见提示；过期项目会占据主要列表。

建议：统一云端同步；显示“已保存/正在同步/同步失败”；增加活动项目、已归档两层视图；所有编辑操作提供撤销或二次确认。

### 3.5 使用 Offer 圈

健康度：发布阻断。

- 页面视觉上像成熟社区，但互动刷新后消失。
- 公开内容与后台零数据不一致，用户无法判断哪些是真实投稿、哪些是官方整理。
- 缺少个人消息、回复提醒、帖子状态和审核反馈。

建议：先做“小而真实”的审核社区，不追求数量。每条内容显示内容类型、发布时间、审核状态；官方整理与用户投稿必须区分；回复、关注、举报形成完整闭环。

### 3.6 寻求咨询与了解平台

健康度：内容完整，行动路径偏弱。

- 关于、数据说明、FAQ 和咨询页整体视觉一致。
- 咨询页缺少明确预约动作；关于页缺少运营主体、更新时间和纠错响应承诺。
- 隐私政策没有充分解释实际数据采集。

建议：补齐运营主体与联系方式、内容更新机制、纠错处理时限；咨询页设置单一行动入口；重写隐私信息层级。

## 5. SEO 与增长审查

1. 所有站内通知详情链接必须统一到静态详情路径；旧查询参数路径做 301。
2. `/about`、`/publish`、`/terms`、`/privacy`、`/disclaimer`、`/community`、`/deadlines` 等页面需独立 title、description、canonical。
3. GitHub 爬虫写数据库后不会自动重建静态详情与 sitemap。应改为 ISR/SSR，或抓取成功后触发验证、构建和部署。
4. sitemap 不应在每次构建时把所有静态页面的 `lastmod` 都写成当前时间，只在内容实际显著变化时更新。
5. 知识内容应拆成独立文章 URL，建立主题集群和内部链接，而不是依赖几个超长页面。
6. Search Console/Bing/百度提交只能帮助发现页面，不能替代 URL、canonical、内容和更新链路治理。

参考：

- Google canonical 指南：<https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls>
- Google sitemap `lastmod` 说明：<https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping>

## 6. 可访问性审查

当前未发现跳至主内容链接，也未实现 `prefers-reduced-motion`。工作台切换控件多数缺少 `role="tab"`、`aria-selected` 等状态语义；若干移动端控件低于成熟产品常用的约 44px 触控尺寸。

建议上线前至少完成键盘操作、焦点可见性、表单错误朗读、对比度和移动端触控检查。WCAG 2.2 的最低目标尺寸标准可参考：<https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum>

本次未安装 axe，也未使用真实读屏软件，自动化无障碍扫描和读屏行为仍是测试缺口。
